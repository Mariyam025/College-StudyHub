Software Testing - Unit 1

1. Introduction to Software Testing

Software Testing is the process of evaluating and verifying a software product to find defects and check whether it satisfies specified requirements.

Testing is performed to improve software quality and increase confidence that the software behaves as expected.

Example:
If a login page requires a valid username and password, testing checks whether the system accepts valid credentials and correctly rejects invalid credentials.

2. Why is Software Testing Needed?

  • To find defects before software is delivered.
  • To verify that requirements are satisfied.
  • To improve software quality.
  • To reduce the risk of software failure.
  • To improve reliability and security.
  • To increase customer satisfaction.
  • To reduce the cost of fixing defects after release.

3. Goals of Software Testing

  • Find errors and defects.
  • Verify software requirements.
  • Validate user expectations.
  • Identify missing functionality.
  • Check software reliability.
  • Provide information about software quality.
  • Reduce the possibility of failures in production.

4. Testing and Debugging

Testing and debugging are related but they are not the same.

Testing Debugging
Finds defects or failures. Finds and fixes the cause of a defect.
Usually performed by testers and developers. Mainly performed by developers.
Shows that a problem exists. Attempts to locate and correct the problem.

5. Principles of Software Testing

1. Testing Shows Presence of Defects

Testing can show that defects exist, but successful testing cannot prove that software contains absolutely no defects.

2. Exhaustive Testing is Impossible

It is generally impossible to test every possible input and situation. Therefore, suitable test cases are selected.

3. Early Testing

Testing activities should begin as early as possible in the software development life cycle.

4. Defect Clustering

A relatively small number of modules may contain a large number of defects.

5. Pesticide Paradox

If the same test cases are repeatedly executed, they may stop finding new defects. Therefore, test cases should be reviewed and improved.

6. Testing is Context Dependent

Testing methods depend on the type of software, risk, requirements and environment.

7. Absence-of-Errors Fallacy

Even if a system has very few known defects, it may still fail to meet the user's actual needs.

6. Error

Error is a human mistake made while designing, coding, understanding requirements or performing another software activity.
Example: A programmer writes + instead of - in a calculation.

7. Fault / Bug / Defect

A fault or bug is an incorrect part of a software product that can cause incorrect behaviour.
Example: The programmer writes the wrong condition:

if(age > 18)

when the requirement actually says that age 18 should also be accepted.

8. Failure

Failure occurs when the software executes and produces an incorrect or unexpected result.
Example: A user enters valid login details but the system displays "Invalid username or password."

9. Incident

An incident is an observed situation or event that requires investigation. It may indicate a defect or unexpected behaviour.

10. Error, Fault and Failure

Term Meaning Example
Error Human mistake Developer writes incorrect formula
Fault/Bug Defect in software Wrong formula exists in code
Failure Incorrect behaviour during execution Wrong answer displayed
Incident Observed event requiring investigation Unexpected application behaviour reported

11. Test Case

A Test Case is a set of conditions, inputs, steps and expected results used to verify a particular software function.

Common Test Case Fields

  • Test Case ID
  • Test Case Description
  • Precondition
  • Input Data
  • Test Steps
  • Expected Result
  • Actual Result
  • Status - Pass/Fail
Test Case ID Input Expected Result
TC01 Valid username and password Login successful
TC02 Wrong password Error message displayed

12. Test Scenario

A test scenario describes what functionality needs to be tested at a high level.

Scenario: Test the login functionality.

Test cases can then check valid login, invalid login, empty fields, password length, etc.

13. Test Suite

A Test Suite is a collection of related test cases grouped together for testing a particular feature or system.
Example: A Login Test Suite may contain 20 test cases.

14. Test Data

Test data is the input data used during testing.

Examples:

  • Valid username
  • Invalid username
  • Valid password
  • Empty password
  • Special characters
  • Boundary values

15. Testware

Testware refers to all documents, scripts, data and other items created or used during software testing.

Examples include:

  • Test plans
  • Test cases
  • Test scripts
  • Test data
  • Test reports
  • Defect reports

16. Software Testing Life Cycle - STLC

The Software Testing Life Cycle is a sequence of activities performed during the testing process.

1. Requirement Analysis

Testers study requirements and identify what needs to be tested.

2. Test Planning

Testing objectives, resources, schedule, tools and strategy are planned.

3. Test Case Development

Test cases and test data are prepared.

4. Test Environment Setup

Hardware, software, database and other required environments are prepared.

5. Test Execution

Test cases are executed and actual results are compared with expected results.

6. Defect Reporting

Detected defects are recorded and communicated to the development team.

7. Test Closure

Testing results, reports and lessons learned are documented after completion.

Requirement Analysis → Test Planning → Test Case Development → Environment Setup → Test Execution → Defect Reporting → Test Closure

17. Verification

Verification checks whether software work products are being created correctly according to specified requirements and design.
Simple question: "Are we building the product right?"

18. Validation

Validation checks whether the developed software satisfies the intended user needs and requirements.
Simple question: "Are we building the right product?"

19. Verification vs Validation

Verification Validation
Checks work products. Checks the final software behaviour.
Mostly static activities. Usually involves execution/testing.
Are we building the product right? Are we building the right product?

20. Static Testing

Static testing examines software documents or code without executing the program.

Examples

  • Requirement review
  • Code review
  • Inspection
  • Walkthrough
  • Static analysis

21. Inspection

Inspection is a formal review process in which work products are examined systematically to identify defects.

22. Walkthrough

A walkthrough is a review in which the author explains the work product to other team members and receives feedback.

23. Technical Review

A technical review examines technical aspects of a software work product to identify problems and improve quality.

24. Dynamic Testing

Dynamic testing involves executing the software and observing its behaviour.

Example: Running a login application with different usernames and passwords.

25. Limitations of Testing

  • Exhaustive testing is generally impossible.
  • Testing cannot guarantee zero defects.
  • Testing can require significant time and resources.
  • Some defects may remain undiscovered.
  • Testing depends on the quality of test cases.
  • Changing requirements can affect testing.

26. Quick Revision

  • Testing finds defects and checks software behaviour.
  • Error = human mistake.
  • Fault/Bug = defect in software.
  • Failure = incorrect behaviour during execution.
  • Test case contains inputs, steps and expected results.
  • STLC describes major testing activities.
  • Verification = Are we building the product right?
  • Validation = Are we building the right product?
  • Static testing does not execute the software.
  • Dynamic testing executes the software.
